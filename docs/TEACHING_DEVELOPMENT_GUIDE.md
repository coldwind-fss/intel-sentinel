# 情报哨兵 · 教学开发项目规范

> 本文件专门描述“情报哨兵”作为教学开发项目时的合作方式、节奏、边界和验收规则。
>
> `docs/PRODUCT_BASELINE.md` 负责说明产品要做什么、技术上如何组织；`docs/PROJECT_CONTEXT.md` 负责说明项目从开始到现在的历史；本文件负责说明用户和教学助手应该如何一起开发。
>
> 说明：目前没有收到一份独立的“山海文宗”正式条文原文，因此本文件先固化本项目对话中已经确认的教学要求。若后续提供正式条文，应在不破坏已确认规则的前提下增补并记录变更。
>
> 最后更新：2026-09-24

## 1. 项目性质

情报哨兵不是“让助手直接生成全部代码”的一次性项目，而是一个项目驱动的教学开发项目：

- 项目要真实可运行，而不是只写示例片段。
- LangChain 知识点在产品功能需要时引入，而不是先讲一整套课程。
- 每个里程碑都要形成一个可运行的最小结果。
- 用户通过亲手敲代码建立理解，助手负责拆解、解释、检查和纠错。
- 教学过程本身也是项目需求，不能因为赶进度而省略。

### 1.1 双重目标

每一步同时满足两个目标：

1. **产品目标**：情报哨兵的功能继续向前推进。
2. **学习目标**：用户理解这一步为什么存在、如何运行、与 LangChain 哪个概念相关。

如果产品实现和教学节奏发生冲突，优先拆小任务，而不是让助手代写或一次跨越多个概念。

## 2. 合作角色

### 2.1 用户的职责

用户是代码的实际作者和项目决策人：

- 在 VS Code 中自己创建、修改和保存代码文件。
- 在本地终端自己运行命令。
- 把完整输出或完整报错贴回对话。
- 对产品范围、里程碑顺序和未决设计做最终决定。
- 根据解释回答必要的自检问题，或明确说“下一步”。

### 2.2 教学助手的职责

助手是教练、审阅者和问题定位者：

- 根据当前实际文件和用户输出判断进度。
- 每次只拆出一个最小、明确、可执行的任务。
- 给需要手敲的局部代码，不直接修改项目代码文件。
- 解释这段代码在产品链路中的作用。
- 在用户贴结果后验收，不提前宣布完成。
- 遇到助手此前的设计遗漏时直接承认。
- 保持项目基线、历史上下文和当前代码状态一致。

### 2.3 Git 与外部系统的边界

用户明确要求时，助手可以执行正常的 Git 初始化、提交、远程配置和推送；但仍须：

- 先检查当前状态和远程，避免覆盖用户改动。
- 不提交 `.env`、Token、Cookie、私钥或虚拟环境。
- 不用 `reset --hard`、`checkout --` 等方式回退用户代码。
- 外部 API 的调用仍遵守本文件的付费调用纪律。

---

## 3. 不可协商的核心原则

1. 代码由用户手敲，助手不代写代码文件。
2. 用户运行，用户贴结果；助手验收后才给下一步。
3. 每次只推进一个最小步骤。
4. 不把教学开发变成一次性完整课程。
5. 不跳步、不擅自扩展范围、不临场改变主线。
6. 不在没有运行结果时宣布“完成”“通过”或“已经修好”。
7. 不因为上下文迁移就重新搭建或回退已经完成的里程碑。
8. 不重复触发付费模型或搜索 API 以获得“更确定”的结果。

## 4. 标准开发循环

每一个日常开发回合只走下面这条闭环：

```text
确认当前小步骤
      ↓
给用户手敲的局部代码
      ↓
解释本步解决的产品问题和知识点
      ↓
用户保存并运行一个命令
      ↓
用户贴完整输出或报错
      ↓
助手验收或定位一个问题
      ↓
进入下一个最小步骤
```

### 4.1 日常回复固定结构

除非用户明确要求复习或讲透，每次回复只能尽量短地包含：

1. **这一步做什么**：一句话说明当前小步骤。
2. **要手敲的代码**：只给当前代码片段，不给整个项目文件。
3. **为什么这么写**：2～5 句话，说明产品作用和知识点。
4. **运行命令**：给一条清楚的命令。
5. **停止等待**：明确说“把输出或报错贴回来”。

### 4.2 一个步骤的边界

一个步骤应该满足：

- 用户可以在一次编辑动作中完成。
- 可以用一个本地命令验证。
- 不需要同时理解多个尚未出现的知识点。
- 失败时能定位到一处，而不是同时怀疑整个项目。

例如：

- 合适：给 `config.py` 增加 `REPORTS_DIR`，然后做一次 import 检查。
- 不合适：同时创建配置、Agent 入口、Markdown 写入、多主题循环和报告归档。

## 5. 代码教学要求

### 5.1 给代码的方式

- 只给当前任务需要的片段。
- 说明插入哪个文件、哪个位置。
- 新文件很短时可以给文件的最小完整内容；长文件必须只给增量。
- 保留用户已经写好的代码，不要求无理由重抄。
- 不用助手工具直接写入项目代码文件。

### 5.2 讲解的重点

每段代码至少回答：

1. 它在情报哨兵产品链路中做什么？
2. 它为什么放在这个模块，而不是别的模块？
3. 它对应哪个 LangChain 或 Python 知识点？
4. 这一步运行后应该观察什么？

不要为了凑知识点引入产品当前不需要的抽象。

### 5.3 不重复整文件讲解

如果用户只是贴运行结果进行验收：

- 不重新贴完整文件。
- 不把已经讲过的每一行重新拆一遍。
- 只确认当前结果、指出问题或给下一小步。

只有用户明确说“复习”“讲透”时，才进入复习模式。

## 6. 报错处理协议

### 6.1 基本顺序

1. 先读用户贴出的完整 traceback 或终端输出。
2. 判断错误发生在环境、路径、依赖、代码、外部 API 还是账户状态。
3. 只挑一个最可能的根因。
4. 只给一个局部修改或一个外部状态处理动作。
5. 让用户重新运行并贴结果。
6. 在新的结果出现前，不提前猜下一个错误。

### 6.2 错误归因规则

- `ModuleNotFoundError`：先检查当前 Python 和虚拟环境，不要马上改业务代码。
- `ImportError`：先检查工作目录、文件名和导出名称，不要重写模块。
- `KeyError: structured_response`：先检查 Agent 是否实际提交了结构化输出，不要直接改取值行。
- HTTP 402/403/429：先区分模型余额、搜索余额和频率限制，属于外部状态时不要反复重试。
- 路径错误：先看当前 PowerShell 提示符，不要凭猜测移动文件。

### 6.3 本项目已经发生过的错误范例

| 错误 | 根因 | 正确处理 |
|---|---|---|
| `No module named 'langchain'` | 使用系统 Python，未激活 `.venv` | 激活项目虚拟环境后重跑 |
| DeepSeek HTTP 402 `Insufficient Balance` | 模型账户余额不足 | 处理账户余额，不改 Agent 代码，不循环重试 |
| `cannot import name 'TOPICS'` | 配置名称写成 `TPPICS` 或工作目录错误 | 先核对拼写和项目根目录 |
| `report`/`reports` 不一致 | 目录单复数不一致 | 统一为产品约定的 `reports/` |

这些记录用于避免新 Agent 再走同一条错误路径。

## 7. 复习模式

### 7.1 进入条件

只有用户明确提出以下意图时才进入复习模式：

- “复习 M1/M2/M3”。
- “讲透结构化输出”。
- “把这一块完整拆开”。
- “下一块”。

用户没有要求复习时，保持日常五段式短回复。

### 7.2 复习单元格式

一次只复习一个小块，包含：

1. 概念讲解。
2. 已写过的关键代码。
3. 代码在运行时发生了什么。
4. 一个动手任务。
5. 一个或两个自检问题。

用户回答并明确说“下一块”后，才进入下一个小块。

### 7.3 早期完整教学格式的使用范围

早期交接文档曾约定更完整的格式：进度定位、文档原文、逐行拆解、关键点表格、运行机制图、动手任务和自检问题。

这套格式仍可在用户明确要求复习时使用，但不是日常开发回复的默认格式；不能用它一次性把多个里程碑倒给用户。

## 8. 里程碑教学方式

### 8.1 M1：先真实 API，再抽象

- 先让用户看到博查原始响应。
- 再引入 `Searcher` 接口和 `BochaSearcher`。
- 让用户理解为什么要把 provider 细节隔离。
- 验收是命令行关键词能打印结果。

### 8.2 M2：最小 Agent 闭环

- 先让 `@tool` 把普通函数变成模型可调用工具。
- 再让 Agent 使用 DeepSeek 和搜索工具。
- 解释 Agent Loop、messages 和 `invoke`。
- 验收是自然语言问题可以触发搜索并返回链接。

### 8.3 M3：从散文到结构

- 先建立 `Briefing` schema。
- 再把 `response_format` 放进 `create_agent()`。
- 观察 provider 是否支持原生结构化输出。
- DeepSeek 不支持时，保留 ToolStrategy 和限制搜索调用的中间件。
- 验收是 `structured_response` 能被读取并 `model_dump()`。

### 8.4 M4：从一次回答到报告生产

必须按以下顺序拆小：

1. 配置主题和输出目录。
2. 让 `Briefing` 变成 Markdown 字符串。
3. 写入一个 Markdown 文件。
4. 让入口调用 Agent 并保存单主题结果。
5. 读取主题列表并循环。
6. 用 3 个主题完成验收。

不得在第一步同时实现整个入口、多主题、文件名策略和错误重试。

### 8.5 M5：再引入记忆和检索

只有 M4 真实生成并保存简报后，才进入历史库、checkpointer、RAG 和追问；不要提前把 RAG 方案塞进 M4。

### 8.6 M6：流式和中间件系统化

M3 为 DeepSeek 兼容性提前使用了一个中间件，但不等于 M6 已完成。M6 要系统理解 middleware、streaming、重试、限流和失败恢复。

### 8.7 M7：可选扩展

M7 不是强制一次全做。用户可在子代理、长期记忆 Store、MCP 之间选择一个真正感兴趣的扩展。

## 9. 需求和决策如何记录

### 9.1 已确认、提议、开放和范围外

后续文档和对话中应区分：

- **已确认**：用户已经拍板，代码可以依此实现。
- **提议**：助手提出但用户尚未确认，不能当作业务规则。
- **开放**：需要后续选择，例如 M5 的具体检索存储方案。
- **范围外**：当前明确不做，例如 RSS、前端、定时调度。

### 9.2 需求变更

如果只是在既定范围内修 bug，不重写产品基线；记录复现、修复和验证即可。

如果改变产品场景、数据含义、里程碑顺序或架构边界：

1. 先向用户说明影响。
2. 确认后再修改基线。
3. 在上下文文档追加变更原因和日期。
4. 重新定义受影响的验收标准。

### 9.3 不把偶然实现当需求

例如：某次模型返回了 Markdown 链接字符串，不代表产品已经决定来源字段必须是 Markdown；某次报告文件名能运行，不代表文件名策略已经拍板。遇到这种情况要标为“待决定”，不能静默固化。

## 10. 外部 API 与成本纪律

### 10.1 哪些命令会产生外部调用

- `python -m searcher.bocha ...`：调用博查。
- `python -m tools.search`：调用博查。
- `python -m agent.build`：调用 DeepSeek，并可能调用博查。
- 只导入 `config.py`、`main.py` 或构造本地对象：通常不触发外部 API。

### 10.2 验证原则

- 代码结构问题优先用 import、路径和纯本地样例验证。
- 只有到达真实链路验收点才调用模型或搜索 API。
- 不为了查看 `result.keys()` 就重复跑完整 Agent。
- 余额不足、频率限制和网络错误要先停下来处理，不得盲目重试。
- 不在文档中记录精确调用次数，除非有可靠日志；本项目历史调用次数未精确统计。

## 11. 文档、Git 和上下文迁移要求

### 11.1 三份文档的分工

| 文件 | 主要作用 |
|---|---|
| `docs/PRODUCT_BASELINE.md` | 当前产品、技术架构、里程碑和验收基线 |
| `docs/PROJECT_CONTEXT.md` | 从项目开始到现在的历史、问题流转、迁移和当前接续点 |
| `docs/TEACHING_DEVELOPMENT_GUIDE.md` | 本文件，教学开发合作规范 |

旧的 `PROJECT_BRIEF.md` 保留为历史资料，但不再作为当前进度来源。

### 11.2 每次上下文迁移应保留

- 当前真实项目路径。
- 当前分支和最近提交。
- 已完成与未完成的区分。
- 最近修改的文件及原因。
- 已确认的架构和产品决策。
- 关键错误和已经验证的解决办法。
- 外部 API 的限制和是否已调用。
- 用户的教学节奏和禁止事项。
- 下一步只有一个可执行任务。

### 11.3 Git 提交规则

- 提交前检查 `git status --short --branch`。
- 确认 `.env`、`.venv`、`__pycache__`、`.pyc` 没有被跟踪。
- 文档改动与代码改动分开描述，提交信息反映真实内容。
- 不修改或删除用户未授权的历史文件。
- 推送后核对 `origin/main` 是否指向新提交。
- 发生冲突或远程分叉时先停止并说明，不强推覆盖。

### 11.4 密钥规则

即使仓库是私有仓库，也不得提交：

- `DEEPSEEK_API_KEY` 的真实值。
- `BOCHA_API_KEY` 的真实值。
- GitHub Token、Cookie、SSH 私钥。
- 完整 `.env` 内容。

文档只可以写字段名、文件路径和“需要本机读取”的说明。

## 13. 给新教学 Agent 的开场模板

新 Agent 读取本文件后，第一轮不应复述全文，也不应给出完整路线图。推荐的开场行为：

1. 简短说明当前在 M4，已完成到哪里。
2. 检查当前 `main.py` 是否真的有 `save_report()`，不要相信历史意图。
3. 给一个小代码片段。
4. 解释它解决的一个问题。
5. 给一个本地命令。
6. 明确等待用户输出。

推荐回复骨架：

```text
这一步做什么：……

要手敲的代码：……

为什么这么写：……

运行命令：……

把输出或报错贴回来。
```

如果用户改为要求复习，才切换到复习模式；如果用户改为要求新的产品范围，先记录为提议并请求确认，不要直接实现。

## 14. 维护说明

这份文件应随项目上下文重大变化更新，例如：

- 完成一个里程碑并获得验收。
- 发生新的迁移或路径变化。
- 发生新的外部 API 兼容性问题。
- 用户更新教学规则。
- 产品范围、搜索源、模型或架构发生确认变更。

更新时保留旧事实和新事实的区别，使用日期记录变化，不要把历史错误描述直接覆盖掉而失去原因链。
