## 1. 项目定位

### 1.1 产品名称

情报哨兵（Intel Sentinel）。

### 1.2 一句话定义

用户配置若干关注主题，Agent 调用联网搜索，去重并摘要，生成结构化 Markdown 情报简报；简报落盘后，用户可以用自然语言追问历史情报。

### 1.3 核心使用场景

| 场景 | 用户动作 | 系统动作 |
|---|---|---|
| 每日简报 | 配置主题，例如“LangChain” | 搜索互联网、摘要、输出主题/要点/来源组成的简报 |
| 追问情报 | 问“最近 LangChain 的 RAG 有什么新特性？” | 从已入库的历史简报检索并带来源回答 |
| 多轮对话 | 问“那和 Graph API 比呢？” | 记住上一轮语境，理解“那”所指内容 |
| 多主题 | 配置多个主题 | 分别搜索并合并成一份简报 |
| 进阶扩展 | 允许 Agent 拆分任务 | 子代理分工、并行抓取或长期保存主题 |

### 1.4 产品边界

当前学习项目阶段暂不做：

- 自动定时调度；先手动跑通完整链路。
- RSS 作为主数据源；产品要求是全网主动监测。
- 自研爬虫作为主线；搜索能力通过 API 抽象。
- Web/前端界面；先完成命令行后端核心。
- 多用户、权限和生产级部署。

## 2. 已确认的产品与技术决策

以下决策来自项目设计和后续教学过程，视为当前基线中的已确认内容：

1. 简报格式为 Markdown，保存到项目根目录的 `reports/`。
2. 当前搜索数据源为博查 Web Search API；不切换到 RSS。
3. 搜索层必须有统一接口 `Searcher`，通过实现类和工厂预留 Tavily、MCP 等扩展口。
4. 当前模型为 DeepSeek `deepseek:deepseek-chat`；`reasoner` 不用于本项目工具调用。
5. 先手动运行跑通全流程，定时运行后置。
6. 先落盘 Markdown，再在 M5 做简报入库与历史追问。
7. 当前项目根目录是中文目录 `情报哨兵`；早期规划中的 `langchain_dev` 不得与当前项目混淆。
8. 用户代码必须由用户在 VS Code 中手敲；助手不得直接修改项目代码文件。

### 2.1 DeepSeek 兼容性决策

DeepSeek 不支持本项目所需的原生结构化输出，因此 `create_agent(response_format=Briefing)` 会使用工具策略。实际运行中，模型可能重复调用 `search_web` 而不提交 `Briefing`，所以 M3 提前使用了原计划在 M6 系统学习的 `ToolCallLimitMiddleware`：

- 只限制 `search_web`，不限制结构化输出工具。
- 每次 Agent 运行最多执行一次 `search_web`。
- `exit_behavior="continue"`，超限搜索被阻止后仍让 Agent 有机会提交 `Briefing`。

这是为模型兼容性做的实现调整，不改变 M1～M7 的里程碑顺序；M6 仍需系统学习中间件、流式、重试和限流。

## 3. 技术架构与依赖方向

```text
入口层 main.py
    ↓
Agent 层 agent/build.py
    ↓
工具层 tools/search.py
    ↓
搜索层 searcher/__init__.py + searcher/bocha.py
```

### 3.1 模块职责

- `config.py`：主题列表和报告输出目录等项目配置。
- `main.py`：入口编排、结构化简报转 Markdown、报告写入以及多主题循环。
- `agent/`：模型、系统提示词、Agent 组装和 `Briefing` schema。
- `tools/`：把业务能力暴露为 LangChain 工具。
- `searcher/`：统一搜索接口、provider 工厂和博查实现。
- `reports/`：生成的 Markdown 简报。

### 3.2 核心数据对象

`agent/schema.py` 中的 `Briefing` 当前字段为：

- `topic`：本次简报主题或搜索关键词。
- `title`：简报标题。
- `summary`：3～5 句话的核心摘要。
- `key_points`：关键要点列表。
- `sources`：信息来源链接列表。

### 3.3 依赖规则

- Agent 只依赖工具接口，不直接写博查 HTTP 细节。
- 工具只通过 `create_searcher()` 使用搜索层。
- provider 更换应只影响 `searcher/`，不应要求修改 Agent 代码。
- `.env` 只存本地密钥，不能进入 Git 或文档正文。

## 4. 里程碑总览与验收标准

每个里程碑都必须有可运行的最小结果；验收以实际命令输出为准，不以代码“看起来完成”为准。

| 里程碑 | 目标与实施内容 | 主要知识点 | 验收标准 |
|---|---|---|---|
| M1 | 博查 API、`Searcher` 接口、`BochaSearcher` 实现、HTTP/业务错误处理 | API 调用、工具底座、接口抽象、错误处理 | 输入关键词，命令行打印搜索结果 |
| M2 | `create_agent` 接入 DeepSeek、搜索工具和系统提示词 | 模型、工具、Agent Loop、messages、分层依赖 | 问“帮我搜 X”，返回带链接回答 |
| M3 | `Briefing` Pydantic schema、结构化输出、DeepSeek 兼容中间件 | 结构化输出、提示词约束、ToolStrategy | 输出包含主题、标题、摘要、要点、来源的结构化结果 |
| M4 | `config.py`、`reports/`、Markdown 转换与写入、多主题循环、`main.py` 入口 | 文件写入、配置设计、循环编排 | 配置 3 个主题后，`reports/` 生成一份 Markdown 简报 |
| M5 | 简报入库、短期记忆、检索与历史追问 | State、checkpointer、thread_id、RAG | 问“上次 X 说了什么”，回答带历史来源 |
| M6 | 流式输出、中间件系统学习、失败重试与限流 | streaming、middleware、重试、限流 | 看到打字机效果，失败可自动重试 |
| M7（可选） | 子代理分工、长期记忆或 MCP 封装，任选其一 | 多智能体、Store、MCP | 至少完成一个进阶扩展并给出可运行验收 |

### 4.1 M4 的明确实施顺序

1. `config.py` 集中定义主题列表和 `REPORTS_DIR`。
2. 创建并保留 `reports/` 输出目录。
3. 在 `main.py` 中把 `Briefing` 转成 Markdown 字符串。
4. 增加报告文件写入函数，使用 UTF-8 保存到 `reports/`。
5. 由入口调用 Agent，并把单主题结果保存为报告。
6. 再把单主题入口扩展为多主题循环。
7. 以 3 个主题生成 1 份 Markdown 简报作为 M4 验收。

## 5. 项目驱动教学规范（不可协商）

这些规则优先于一般的“自动完成代码”习惯，是本项目的一部分需求。

### 5.1 核心原则

1. 用户写代码，助手教学；助手绝不代写代码文件。
2. 用户运行命令并贴结果；助手根据结果验收，再给下一步。
3. 每次只推进一个最小步骤。
4. 这是开发真实项目并伴随教学，不是先上完整课程再写项目。

### 5.2 日常开发回复格式

除非用户明确要求复习或深入讲解，每次只包含以下五部分：

1. **这一步做什么**：一句话说明当前小步骤。
2. **要手敲的代码**：只给当前这一小段，不贴整个项目文件。
3. **为什么这么写**：用 2～5 句话说明项目作用和涉及的知识点。
4. **运行命令**：明确告诉用户执行哪条命令。
5. **停止等待**：明确要求用户把输出或报错贴回来。

### 5.3 明确禁止

- 不替用户创建或修改项目代码文件。
- 不在用户未贴运行结果前宣布“完成”或“通过”。
- 不因为用户贴了交接文档就重新搭建项目。
- 不一次输出完整教案、完整路线图或多个后续步骤。
- 不在代码已经写好、用户只是验收时重新逐行讲完整文件。
- 不擅自跳到后续里程碑或替用户决定未确认的产品范围。
- 不擅自安装依赖、清理文件、改名或改变既定主线。
- 不重复触发付费模型或搜索 API 调用来“确认一下”。

### 5.4 报错处理

1. 先要求用户贴完整报错。
2. 只定位一个最可能的问题。
3. 只给这一处修改片段或一个外部状态处理动作。
4. 让用户重新运行并贴结果，再判断下一个问题。
5. 如果问题源于助手之前的设计，直接承认是设计遗漏。

### 5.5 复习模式

只有用户明确说“复习”“讲透”或类似请求时，才切换到复习模式：

- 一次只复习一个小块。
- 每块讲概念、关键代码、动手任务和自检问题。
- 用户回答并说“下一块”后再继续。
- 复习是讲透已写内容，不是重写项目代码。

### 5.6 语言与节奏

- 使用中文。
- 能短则短，术语第一次出现时只做一句话解释。
- 让用户明确感到代码是自己亲手敲出来的。
